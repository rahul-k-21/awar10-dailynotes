
Without ISTIO:
- Any microservice can talk to other microservices directly. 
- No visibility into who is talking to whom.
- no control over encryption or traffic rules. 


With ISTIO : 
- Every service gets a sidecar container. Technically we call it an Envoy proxy. 
- This will be automatically injected. All traffic flow goes through this proxy only. 
- 


North-South Traffic : It acts as a front door and back door of our application. 
- Whatever client request comes from the outside world, it will be picked. 
- We have a lot of options like ingress controllers and Kubernetes services, like NodePort and load balancer. These components take the traffic from the outside world from the clients and send traffic to Kubernetes cluster's internal workloads. 

East-West Traffic : East-west traffic represents internal service-to-service communication. East-west traffic typically forms the vast majority of total network data inside a cluster. 

- It will be managed by CNI (container network interfaces).
- Pods do not directly communicate with other pods.
- Pods will use services like a cluster IP primarily to communicate with other services. 


---

1. istiod / Control Plane : this is the brain of Istio. It has multiple components like a pilot - traffic rules, citadel - certificates, and galley - configuration validation. 
2. Side care container / Envoy proxy
3. mTLS / peer authentication :
	3.1 STRICT : only mTLS is accepted. Any plain HTTP request will be rejected. 
	3.2 PERMISSIVE : accepts plain HTTP request as well as MTLS request.  (Default)
4. Gateway : gateway manages inbound traffic from outside of the cluster, similar to an ingress controller or load balancer, and it works with the Kubernetes Gateway API.
