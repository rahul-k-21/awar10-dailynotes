K8s Architecture : 

Conrol Plane : brain of K8s
Data Plane : Hands of K8s


1. CONTROL PLANE COMPONENTS : 

1.1 kube-apiserver / apiserver : 
--> This is the front door of Kubernetes. This is the single point of contact to communicate with the Kubernetes cluster. 
--> If you want to deploy any workload, if you want to view the existing workload, or if you want to delete the existing workload, you communicate with the Kube API server by using "Kubectl". 
--> KubeAPI server validates the configuration (pod, service, deployment). 

kubectl apply -f file1.yaml  10 pods --> 
kubectl apply -f file2.yaml
kubectl create ns myapp
kubectl delete ns myapp

1.2 etcd (etc distributed) : (tradiitonal linux hasve its all config in /etc they picked same and k8s works across nodes so, they add d - distribution) 
- ETCD contains all the information about a Kubernetes cluster, its configuration, and its workload.
- In ETCD all the information is stored in key-value pairs.
- Treat ETCD as the Kubernetes full-fledged database.
- It stores the current and desired state of the cluster.  5 pods existing --> 5 new pods
- If we lose access to etcd, our cluster state is lost. 
- STRICT COMMUNICATION : no component in Kubernetes speaks to etcd directly except the API server. Everything else (scheduler, controller manager) goes through the API server to read and write data. 

1.3 kube-scheduler : 
- It looks for an available worker node to run our workload based on node resource utilisation, like CPU or memory. 
- When it wants to run the pod, it will pick the best node to run our workload. 

1.4 Kube-Controller-Manager : 
- Kube-Controller-Manager acts as a supervisor.
- This firstly monitors "etcd" and ensures our application's current state matches the desired state.
- If we ask for 10 replicas and only 5 are running, it sends instructions to kube-scheduler to pick the node.
- Kube-Controller-Manager runs in the background in a loop. It always checks with etcd and makes sure the desired state matches the actual state.

1.5 Cloud-Controller-maneger: this will extend Kubernetes capabilities to cloud resources to utilise IAM roles, VPC, load balancers, EFS, and EBS components. 


2. DATA PLANE / WORKER NODE : 

2.1 kubelet : 
- Kubelet is an AGENT that runs in every worker node. 
- Kubelet listens to all the control plane instructions and ensures our containers (described in the pod) are running and healthy. 
- If any container goes down, kubelet will restart it automatically. 

2.2 kubeproxy : 
- Kube-proxy is a networking component. This also runs on every node, similar to kubelet. 
- Kubeproxy assigns an IP address to every pod created on the worker node. 
- The primary purpose is to handle network communications inside and outside of the cluster. Kube-proxy ensures traffic reaches the right container. 

2.3 container runtime : 
- Container runtime is responsible for pulling images and running containers. 
- k8s uses containerd / CRI-O as runtime from version 1.24. (earlier used docker)
- Kubelet sends instructions to the container runtime to pull the image and start the container inside the pod.

EKS (Elastic Kubernetes Service): This is an AWS fully managed Kubernetes service. AWS takes care of all the control plane components. 

For high availability and fault tolerance, AWS maintains multiple copies, at least six copies across three availability zones, which will be maintained or managed by AWS.

Limitations:
- We cannot access control plane nodes.
- We don't get the option to see where those control plane nodes are running.

Amazon EC2 Managed Node Group : **
- AWS automatically provisions and configures managed instances. 
- We need to handle the scaling. We have the option to choose the right-sized EC2 instances. 
- On our behalf AWS will manage the patching and scaling of the instances. 

Amazon EC2 Self managed Node group : 
- We manually need to provision and configure the EC2 instances. 
- We need to handle the scaling, OS operations, and security patches. 

EKS AutoMode : AWS automatically picks the specific configuration of EC2 instances and it costs us very, very little as AWS uses mostly its unused EC2 instances. 

AWS Fargate : this is a serverless: no worker nodes to manage. Our pods are going to run directly. It is very little used as we have limitations: resource limitations and compliance issues, compliance requirement issues.

Resource Limiting : we can define how much memory and CPU should be allocated to the container. If we don't define this value how much memory or CPU available on the underlying host will be allocated to the container.

kube-scheduler uses the allocated resource values to find the appropriate cluster node. If no node has enough capacity, the pod won't be scheduled. It will be in a pending state only. 

Requests : Guranteed Minimum : The Minimum CPU/Memory K8s guarantees to allocate to container.
Limits : Hard Ceiling : The MAXIMUM CPU/memory a contianer is permitted to consume/allocated. This prevent a single container to consume all the resources. 

Memory : 
Megabytes: M
Mebibytes: Mi

CPU Measured in millicores / cores:

Service : services act as a stable network abstraction over an ephemeral group of pods. Parts will be regularly created and destroyed. Their IP addresses are not constant. 

1. ClusterIP (Default) : Cluster IP exposes the services with an internal IP address within the cluster. 

--> Works only internally within the cluster.
--> CLusterIP creates a stable IP address, but this IP works only within the cluster.
--> Treat it as "Internal Load Balancer" / "Intercom Systems".

To test the output in our local laptop, We need to perform port-forward:

kubectl port-forward svc/cip-service 8080:80

** All internal services will be configured to communicate with cluster IP only. 

---

To get output directly from a pod for testing purposes: 

kubectl port-forward pod/mynginx-854864cc7c-pn22b 8080:80

---

2. NodePort : NodePort builds on top of ClusterIP by opening a static port on every node's IP address. 

Port Range : 30000 - 32767

NodePort has specific range to map at node level (30000 - 32767).
We can choose a port manually. If we don't choose, the system will pick automatically. 
We can deliver output to the outside world by using the node IP address. 
The random port needs to be opened at the EC2/Node security group level. 

We can deliver output to the outside world but via node IP address. It is a superset of cluster IP. For local developments we use this not at production level.

Namespace : helps to manage our workload with logical isolation. 

default : This is a default namespace picked by our workload if we don't specify any namespace in our manifest file.

Daemonsets: this will ensure exactly one copy of a specific pod runs on every single worker node we have in our EKS cluster. 
--> If we add a new node to the cluster, a new node will get a daemon set automatically. 
--> This is commonly used for monitoring tools, log exports, or network traffic filters at the node level. 

We don't run our regular workload with daemon sets. We use deployments to run our regular workload. 
When we are using a deployment we can define how many replicas we want but when working with a daemon set it picks the same node count.

pv : Persistent Volume : Storage resources in our cluster or AWS service (example: EBS, EFS) 
pvc : Persistent Volume Claim : a request for storage against the PV.

By default all pods get ephemeral storage. Data will be deleted along with the pod. 

pod --> pod needs the storage --> PVC (Request) --> PV (Actual Storage) --> EBS/EFS


Provisionin options:
Dynamic Provisioning : We can create only PVC. It uses addl helper "StorageClass" to build the storage.
Static Provisioning : We need to create PV and PVC explicitly to get the storage.

AccessModes on Storage: 
RWO : ReadWriteOnce : EBS (gp2, gp3, io1, io2) : One node can read/write.
RWX : ReadWriteMany : EFS : Multiple Nodes can read/write
ROX : ReadOnlyMany : Multiple Nodes can read
